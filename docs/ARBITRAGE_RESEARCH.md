# Арбитраж — оценка прибыльности и требований к инфраструктуре

**Дата начала:** 2026-04-16
**Статус:** Активное
**Последнее обновление:** 2026-04-16 (после probe источников)

## Цель

Ответить на вопрос: **какая инфраструктура окупается под cross-exchange spot арбитраж**?

Сделать это дешёвыми средствами — с минимумом расходов и времени — прежде чем вкладываться в Phase 2-4 (WS-стек, TimescaleDB pipelines, risk-менеджер, OMS).

## Гипотезы

1. **H1:** На Binance/Bybit/OKX по BTC/USDT и ETH/USDT регулярно возникают окна с чистой прибылью после комиссий (≥20bps round-trip).
2. **H2:** Длительность окон > 1 секунды → достаточно Python + REST/WS (Phase 1-2 стек без Rust).
3. **H3:** Частота и размер окон оправдывают инженерные затраты.

Если **H2 ложна** (окна < 100мс) — меняется стек и бюджет проекта.
Если **H1 ложна** — сворачиваем cross-exchange spot, пивот на другой тип арба.

## Findings от 2026-04-16 (probe источников данных)

**Исторический L1 bookTicker бесплатно не достать ни на одной бирже:**

| Источник | Что есть | Что нет |
|---|---|---|
| `data.binance.vision/spot/` | klines, trades, aggTrades — все периоды | bookTicker **вообще никогда** |
| `data.binance.vision/futures/um/` | klines, trades; bookTicker **только за узкое окно ~март 2024** | свежих L1 нет (2024-04 → 404) |
| `public.bybit.com/trading/` | daily csv.gz — судя по именам trades | L1 bookTicker не выкладывают |
| OKX data-download | TBD | TBD |

**REST API с ключом не помогает:** ни Binance, ни Bybit, ни OKX не выдают исторические bid/ask через API. Только orderbook snapshot на текущий момент. Это фундаментальное свойство CEX — исторические котировки коммерческий продукт.

**On-chain тоже не помогает:** CEX-сделки happen off-chain (записи в БД), в блокчейн попадают только движения капитала (депозиты/выводы). Нельзя восстановить orderbook. On-chain полезен для exchange flows + CEX-DEX арба — это отдельное направление, добавлено в `PLAN.md` Backlog.

**Вывод:** для бесплатного L1 варианта только один путь — **собственный WS-collector**, но он требует 2-4 недели ожидания. Для быстрого ответа — **trades-based proxy** (план B) или **платный Tardis.dev** (план D).

## Методология — trades-based proxy

### Идея
У aggTrades (Binance) есть флаг `isBuyerMaker`. Он восстанавливает агрессивную сторону:
- `isBuyerMaker=true` → taker продавал → сделка по **bid** → `price ≤ real_best_bid`
- `isBuyerMaker=false` → taker покупал → сделка по **ask** → `price ≥ real_best_ask`

У Bybit / OKX аналогичное поле `side` (Buy/Sell) — означает **taker side**.

### Построение proxy в окне 1 секунды
```
bid_proxy_t = max(price | side=sell)   # верхний ориентир bid
ask_proxy_t = min(price | side=buy)    # нижний ориентир ask
```
Это **нижняя граница quoted-спреда** — реальный спред шире или равен:
- Если proxy показывает арб **есть** → он гарантированно есть с запасом
- Если proxy показывает арба **нет** → возможно, quoted-уровень всё равно имеет небольшой, но маловероятно крупный

Для «есть ли смысл вкладываться в инфру» этого достаточно.

### Forward-fill
Если в секунде нет trade нужной стороны — берём последнее известное значение (но не дальше N секунд, по умолчанию 30с — дальше считаем unknown).

### Детекция окна
Для каждой 1с-ячейки и каждой пары:
```
best_bid_proxy, exch_sell = max над всеми биржами
best_ask_proxy, exch_buy  = min над всеми биржами
если exch_sell == exch_buy: skip

gross_bps = (best_bid_proxy - best_ask_proxy) / best_ask_proxy * 10_000
fee_bps   = fee_buy + fee_sell  (default 20bps round-trip)
net_bps   = gross_bps - fee_bps

net_bps > 0 → окно
```

### Статистика
- Число окон за месяц (всего и по парам)
- Распределение длительности (1с, 5с, 10с, 1мин, дольше)
- Распределение прибыли (bps): медиана, p90, p99, max
- Топ направлений (A→B, B→C и т.д.)
- Время суток: когда чаще
- Корреляция с волатильностью базового актива

### Выводы про инфраструктуру

| Медианная длительность окна | Вывод |
|---|---|
| > 5 секунд | Python + REST достаточно, Phase 1-2 ок |
| 1-5 секунд | Python + WS, оптимизированный async |
| 100мс-1с | Python на пределе, думать про Rust для hot path |
| < 100мс | Без colocation/FPGA не играем, пивот |

**Важно:** эти выводы применяются только если **Этап 2 (Tardis)** подтвердит, что trades-proxy адекватно описывает quoted-уровень. На proxy длительность может быть искажена (зависит от частоты сделок, а не котировок).

## Этап 2 — Tardis sample (после Gate 1)

**Триггер:** Этап 1 показывает положительный сигнал (≥ N окон/сутки, оценим пороги после первых цифр).

### Наблюдения

1. **Окна существуют**, но их мало и они короткие.
2. ETH даёт ~4× больше окон чем BTC — менее ликвидная пара → шире спреды. Гипотеза: альткоины могут показать ещё лучше.

4. Часовой пик в 11 UTC (Европа утро + США ночь) и 22 UTC (США вечер + Азия утро).
5. **Длительность 1с на proxy ≠ 1с на quoted-уровне.** Trades-proxy отражает только моменты сделок. Реальные quoted-окна могут держаться значительно дольше. Это ключевой вопрос для Gate 2.

| Ресурс | 2 пары | оценка на 10 пар | на 50 пар |
|---|---|---|---|
| Raw данные | 1.7 GB | ~8.5 GB | ~43 GB |

Узкое место — Binance aggTrades (самые большие файлы). При необходимости normalize можно параллелить через `multiprocessing`, будет линейный speedup.

**Вывод по стоимости:** добавление любого числа пар бесплатно и дёшево по ресурсам, даже 50 альткоинов уместятся в пределах ноутбука.

### Решение по Gate 1 — **зелёный, идём на Этап 2**

**Почему ДА:**
- Окна есть (особенно на ETH), p99 прибыли 27-36 bps — приличные
- Trades-proxy — **нижняя граница** реальности, quoted-окна могут быть длиннее
- Стоимость валидации через Tardis sample (≤$50) несоизмеримо меньше стоимости ошибки (потратить месяц на WS-инфру впустую)

**Почему осторожно:**
- Медиана длительности 1с на proxy — тревожный сигнал. Если на L1 та же цифра — Python будет на пределе даже с геолокацией у биржи
- Net_bps медиана 4-5 bps — впритык, любая ошибка latency/slippage съест прибыль

**Конкретный план Этапа 2:**
1. Tardis free-tier: sample на 1-й день марта 2026 (если есть в free). Иначе — pay-as-you-go 1-3 дня из марта, бюджет **до $50**.
2. Прогнать существующий детектор на L1 данных (добавить парсер Tardis формата).
3. Сравнить: для каждой арб-секунды из proxy — какая длительность и net_bps были на L1?
4. Вывод Gate 2: если длительность L1 ≥ 10с — строим WS. Если ≤2с — пивот.

### Precision/Recall PROXY vs L1 OPT
- BTC: Precision 93%, Recall 93%
- ETH: Precision 85%, Recall 73%

**Вывод #1: trades-proxy оказался валидным** — 85-93% совпадение с L1 на уровне arb-секунд. Tardis paid месячной подписки **не нужен** — proxy достаточен для структурных выводов.

**Вывод #2 (ключевой): L1 SNAP даёт 0 окон.** Если опрашивать orderbook раз в секунду — **не увидеть ни одного арба**. Все окна закрываются **внутри секунды**. Реальные окна имеют длительность **миллисекунды**.

**Вывод #3:** Все окна на L1 OPT — ровно 1 секунда или меньше. Это предел resolution нашего per-second анализа. Реальный horizon — **сотни миллисекунд**.

## Gate 2 решение — жёлтый с пивотом

Cross-exchange spot арб **технически возможен**, но требует:
- **Colocation (VPS в регионе биржи)** — без этого REST round-trip съест всё окно
  - Binance — AWS Tokyo, Bybit — AWS Singapore, OKX — AWS Hong Kong
  - Минимум VPS Tokyo + Singapore ~$50/мес
- **WS receive + минимальный Python stack** — Rust не решает (сеть > CPU)
- **Конкуренция с market makers** — они уже colocated во всех регионах, у них FPGA/C++. Наш реалистичный fill rate 20-40%.

**Оценка экономики:**
- 63 окна/сутки × 30% fill × 4 bps × $10k капитала = **~$75/сутки = $2250/мес** на $10k
- С учётом VPS, slippage, ошибок: **$1500-2000/мес**
- Годовой ROI **~20%** на $10k — приемлемо, но **не главный трек**

**Решение:** **перенести cross-exchange на конец очереди**. Строить WS+colocation-стек только когда готова вся остальная инфраструктура (OMS, risk, мониторинг). Тем временем — параллельные треки.
